# Clove Browsing Performance Feasibility Report

- **Date:** 2026-11-14
- **Baseline revision:** `022dc9b` (`main`)
- **Scope:** End-to-end photo-browsing performance across grid scrolling, detail navigation swipes, focus/sharpness analysis, similarity grouping, concurrency and memory management, device spread (iPhone, iPad Pro, Duo split), and folder open / startup.
- **Method:** Full static audit of `Clove`, `CloveCore`, `CloveImaging`, and `CloveLabKit`, paired with Debug and Release runs of the Q3 `BrowsingPerformanceProbe` on `browsing-2000` (4,000 files / 2,000 photo sets) and a standalone Release micro/meso-benchmark harness (`PerfBench`) exercising production `CloveCore` and `CloveImaging` APIs across six RAW camera formats (`5.1 MP` to `26.0 MP`).

---

## 1. Executive Summary

Clove's core architecture—bounded actor queues, Dispatch-backed image workers (`ImageWorkExecutor`), explicit file-revision keys, and compact non-pixel metadata stores—is sound. Most user-visible latency and frame-drop risks do not come from slow system decoders alone; they come from **contention between interactive and background pipelines**, **blocking work placed ahead of first-pixel delivery**, **unnecessary work repeated on `@MainActor` or warm cache opens**, and **three blind spots in the existing Q3 benchmark** that masked 20–50 MP RAW behavior on high-pixel-count displays.

Specifically, four structural findings explain the hitches observed on iPad Pro ([#253](https://github.com/mimiqdev/cloveapp/issues/253)) and frame-budget pressure at 2,000-photo scale:

1. **Sharpness analysis races interactive detail viewing for the single uncancellable `.render` lane.** Because `showsFocusRegions` defaults to `true` and `DetailMarkingView` launches `loadFocusRegions` simultaneously with `loadPreview` (even when `showsFocusRegions == false`), `RegionSharpnessAnalyzer` routinely acquires `DetailPipeline`'s sole `.render` worker for an uncancellable full-sensor `nativeRAW` decode (`382–484 ms` on 20–26 MP RAWs on M2 Pro) while `loadPreview` is still reading the embedded preview. `DetailPipeline` neither reuses that `nativeRAW` for `screenRAW` nor cancels `.analysis` jobs in `beginNavigation`, stalling `screenRAW` (`p95` jumps from `406 ms` to `795 ms` at 800 ms review cadence and `1,209 ms` at 400 ms culling cadence on 20 MP Canon R6 CR3) and starving `+1` neighbor prefetch (`33%` hit rate vs `92%` uncontended). Worse, `RegionSharpnessAnalyzer` unconditionally decodes full `nativeRAW` before checking whether a photo has zero AF metadata and zero detected faces.
2. **Cold detail preview latency is inflated 2–3× by synchronous `CIRAWFilter` initialization and JPEG re-encoding, and swipes wait for `screenRAW` before prefetching neighbor previews.** Before `DetailPipeline.preview` returns an embedded JPEG preview (`13–67 ms` raw ImageIO decode), it synchronously initializes `CIRAWFilter` just to read `outputImage.extent` (`40–87 ms`) and re-encodes the preview to JPEG 0.9 (`9–18 ms`), pushing cold first-preview latency to `105–166 ms`. Meanwhile, `DetailMarkingView` clears `shown = nil` before checking memory caches (guaranteeing at least a one-frame blank flash) and delays `±1` preview prefetch until *after* `screenRAW` finishes (`0/12` prefetch hits during 400 ms brisk culling on 20 MP CR3).
3. **Grid cells always configure asynchronously through `nil` and cancel their own in-flight prefetches.** `GridPhotoCell.configure` unconditionally clears the displayed image, builds a `UIHostingConfiguration` with `nil`, spawns a task, and rebuilds the hosting hierarchy when the image arrives (up to three times per collapsed burst stack). `GridCollectionView.willDisplay` calls `cancelPrefetch` as a prefetched cell enters the viewport, discarding partially decoded work because `ThumbnailPipeline` lacks in-flight request coalescing. In addition, `ThumbnailCache` (`64 MiB`) holds only ~157 decoded 400 px bitmaps (`7.8%` of a 2,000-photo folder) and executes a `setAttributes([.modificationDate])` (`utimes`) syscall on every disk-cache read hit.
4. **Warm folder opens run a redundant 2,000-photo feature pass and recreate every disk cache from scratch.** `FolderGrouping.startAnalysis(needsAnalysis:)` ignores `needsAnalysis == false` after a `SimilarGroupsCache` hit, statting 2,000 files, reading 1,975 cached `.feature` plists, touching `utimes` on each, and calling a no-op `refine()` (`426 ms` Release / `749 ms` Debug vs `10.0 ms` when skipped—and triggering full Vision recomputation if `ImageFeatureCache` evicted entries). Separately, `FolderLibrarySession.makeCaches()` instantiates new `ThumbnailCache`, `ImageFeatureCache`, and `RegionSharpnessCache` objects on every folder open, discarding all warm in-memory tiers and re-scanning cache directories on disk.

## 2. Current Implementation Map

### 2.1 Grid Scrolling & Thumbnail Pipeline

- **Pipeline & concurrency:** [`ThumbnailPipeline`](../../Packages/CloveImaging/Sources/CloveImaging/Thumbnails/ThumbnailPipeline.swift) is an actor with `workerCount = 4` and `queueLimit = 64`. Visible jobs insert FIFO ahead of `.prefetch` jobs; queue overflow evicts the oldest queued `.prefetch` job before throwing `.queueFull`. Decode work hops to [`ImageWorkExecutor`](../../Packages/CloveImaging/Sources/CloveImaging/ImageWorkExecutor.swift) (`userInitiated` for `.visible`, `utility` for `.prefetch`, each backed by a concurrent `DispatchQueue` gated by a `CountingGate` of `min(4, activeProcessorCount)`).
- **Extraction & cache:** [`ThumbnailExtractor`](../../Packages/CloveImaging/Sources/CloveImaging/Thumbnails/ThumbnailExtractor.swift) requests 400 px thumbnails via `CGImageSourceCreateThumbnailAtIndex` (`embeddedOnly` → `ifAbsent` for RAW/HEIF; `embeddedOnly` → `always` for raster formats). [`ThumbnailCache`](../../Packages/CloveImaging/Sources/CloveImaging/Thumbnails/ThumbnailCache.swift) maintains a `Mutex`-protected in-memory LRU (`64 MiB` by `bytesPerRow * height`) and an app-private JPEG 0.85 disk tier (`512 MiB` under `Library/Caches`), keyed by SHA-256 of `(path, locationIdentity, size, mtime.bitPattern, targetPixels, route, version)`. Every disk hit rewrites the cached file's `modificationDate` via `FileManager.default.setAttributes` (`ThumbnailCache.swift:160-161`).
- **App bridge & cell lifecycle:** [`PipelineGridThumbnails`](../../Clove/Grid/PipelineGridThumbnails.swift) detaches via `Task.detached(priority: .userInitiated)` (bypassing `ImageWorkExecutor` and promoting `.prefetch` to `.userInitiated` during revision reads), calls `ThumbnailRevision.read` (`stat`), and forwards to `ThumbnailPipeline`, which calls `ThumbnailRevision.read` two more times on a cache miss (`ThumbnailPipeline.swift:145, 168`). [`GridCollectionView`](../../Clove/Grid/GridCollectionView.swift) drives a 3-column (compact) or `floor((width + 2) / 142)`-column (regular, ~7–9 columns on iPad Pro) compositional layout via `NSDiffableDataSource<Int, GridItem>`. [`GridPhotoCell.configure`](../../Clove/Grid/GridPhotoCell.swift) cancels prior tasks, sets `thumbnail = nil`, assigns a SwiftUI `UIHostingConfiguration` hosting [`GridTile`](../../Clove/Grid/GridPhotoCell.swift) (with nested `GeometryReader`s in `GridTile` and [`GroupStack`](../../Clove/Design/GroupStack.swift)), and launches up to three async thumbnail tasks (representative + two peeking stack members), rebuilding `contentConfiguration` as each finishes. In `collectionView(_:willDisplay:forItemAt:)` (`GridCollectionView.swift:538`), the coordinator calls `cancelPrefetch(item.id)` immediately before the cell's own `loadThumbnail` task starts.

### 2.2 Detail Navigation Swipes

- **Two-lane actor & render serialization:** [`DetailPipeline`](../../Packages/CloveImaging/Sources/CloveImaging/Detail/DetailPipeline.swift) separates `.preview` (`previewWorkers = 2`, embedded previews and display-sized rasters) from `.render` (`activeRenderCount < 1`, serializing `screenRAW`, `nativeRAW`, and `fullRaster`) under a shared `queueLimit = 16`. Once admitted to `.render`, `CIRAWFilter` / `CIContext.createCGImage` in [`DetailRenderer`](../../Packages/CloveImaging/Sources/CloveImaging/Detail/DetailRenderer.swift) cannot be interrupted mid-flight; obsolete `.best` jobs drain without publishing, while running `.screen` jobs continue into [`DetailCache`](../../Packages/CloveImaging/Sources/CloveImaging/Detail/DetailCache.swift) (`retainsRunningScreen = true`).
- **Compressed memory cache:** `DetailCache` holds one uncompressed `native` `DetailImage` for the active photo/mode (`released` on photo or mode change) plus a `64 MiB` in-memory LRU of [`DetailCompressedImage`](../../Packages/CloveImaging/Sources/CloveImaging/Detail/DetailCompressedImage.swift) entries re-encoded as JPEG 0.9 (`embeddedPreview`, `displayRaster(edge)`, and `screenRAW(edge)`). Every cache hit decodes JPEG bytes on a worker thread (`4–16 ms`).
- **Arrival sequence & prefetch:** On swipe or filmstrip tap, [`DetailMarkingView.loadPreview`](../../Clove/Detail/DetailMarkingView.swift) (`lines 736-939`):
  1. Reserves generation via `beginNavigation`, clears `shown = nil; phase = .placeholder(nil)`, and awaits `images.placeholder` (`ThumbnailPipeline` 400 px);
  2. Awaits `images.preview` (`DetailPipeline.preview`), which calls [`DetailNativeSizeReader`](../../Packages/CloveImaging/Sources/CloveImaging/Detail/DetailNativeSizeReader.swift) (`CIRAWFilter(imageURL:)?.outputImage?.extent`), extracts the ≤2,000 px embedded preview, JPEG-0.9 encodes it for `DetailCache`, and returns;
  3. Calls `renderFitAndPrefetch`, which awaits `images.screen` (`CIRAWFilter` scaled to `screenPixels = Int(max(screen.nativeBounds.width, screen.nativeBounds.height))`, draft off, RGBA8 sRGB) and **only after `screen` completes** prefetches `±1` embedded previews and `+1` `screenRAW` in the travel direction.

### 2.3 Focus & Sharpness Analysis Pipeline

- **Engine & early AF:** [`RegionSharpnessAnalyzer`](../../Packages/CloveImaging/Sources/CloveImaging/Sharpness/RegionSharpnessAnalyzer.swift) executes four gated stages: `.metadataRead` (ImageIO properties + `CameraFocusMetadata` AF boxes; delivers `.noAutofocusMetadata` immediately via `onAutofocus`), concurrent `.faceDetection` (`800 px` preview via `DetailPipeline.analysisPreview` + `VNDetectFaceLandmarksRequest`), `.pixelAcquisition` (`DetailPipeline.analysisImage` → full-resolution raster or `nativeRAW`), and `.regionScoring` (`RegionSharpnessScorer`, delivering AF scores before awaiting face detection).
- **Prioritized scheduler & disk tier:** [`RegionSharpnessScheduler`](../../Packages/CloveImaging/Sources/CloveImaging/Sharpness/RegionSharpnessScheduler.swift) enforces stage budgets (`metadata = 2`, `detection = 1`, `acquisition = 1`, `scoring = 2`) across four priorities (`.current < .group < .nearby < .folder`) without mid-stage preemption. [`RegionSharpnessResultStore`](../../Packages/CloveImaging/Sources/CloveImaging/Sharpness/RegionSharpnessResultStore.swift) keeps 512 compact records in memory, backed by [`RegionSharpnessCache`](../../Packages/CloveImaging/Sources/CloveImaging/Sharpness/RegionSharpnessCache.swift) (`16 MiB` JSON files in `Library/Caches`, `#239`).
- **Detail coupling:** [`DetailMarkingView`](../../Clove/Detail/DetailMarkingView.swift) (`lines 169-174, 807-825`) triggers `loadFocusRegions` via `.task(id: photo.id)` concurrently with `loadPreview`, regardless of `model.showsFocusRegions`. [`PipelineDetailImages.analyzeRegions`](../../Clove/Detail/PipelineDetailImages.swift) (`lines 207-237`) synchronously calls `DetailSource.read` (`stat`) on `@MainActor` for `current + group + nearby (±2)` photo sets, submits group/nearby jobs, and awaits `scheduler.analyzeCurrent`. [`DetailRegionSharpnessReading`](../../Packages/CloveImaging/Sources/CloveImaging/Sharpness/DetailRegionSharpnessReading.swift) (`lines 54-59`) constructs `DetailRequest` with default `mode: .rawFirst`, forcing `nativeRAW` even when the user selected `cameraPreviewFirst`.

### 2.4 Similarity Grouping Pipeline

- **Two-stage grouping:** [`FolderGrouping`](../../Clove/Grouping/FolderGrouping.swift) waits until scan summary + all metadata capture-time batches complete (`Note` in `FolderGrouping.swift:12-16`), then runs [`SimilarGrouping`](../../Packages/CloveCore/Sources/CloveCore/Grouping/SimilarGrouping.swift) over candidate bursts (`Δt ≤ 3.0 s`, matching camera body). If [`SimilarGroupsCache`](../../Packages/CloveCore/Sources/CloveCore/Grouping/SimilarGroupsCache.swift) (`Application Support`, validated against candidate IDs, capture times, and sensitivity) hits, `SimilarGrouping` publishes `.analyzed` groups immediately (`needsAnalysis = false`).
- **Feature extraction & warm-open bug:** [`ImageFeaturePipeline`](../../Packages/CloveImaging/Sources/CloveImaging/Features/ImageFeaturePipeline.swift) (`workerCount = 2`, `queueLimit = 64`) extracts 400 px previews, computes 64-bit dHash + [`VisionFeaturePrintReader`](../../Packages/CloveImaging/Sources/CloveImaging/Features/VisionFeaturePrintReader.swift) (`VNGenerateImageFeaturePrintRequest` rev 1/2), and stores ~3.3 KiB binary plists in [`ImageFeatureCache`](../../Packages/CloveImaging/Sources/CloveImaging/Features/ImageFeatureCache.swift) (`4 MiB` memory / `8 MiB` disk ≈ 2,400 entries). In `FolderGrouping.startAnalysis` (`lines 238-254`), `analyse(candidates)` runs unconditionally even when `needsAnalysis == false`, reading every candidate's revision and feature file before calling `grouping.refine()`, which immediately exits on `guard !cacheIsAuthoritative`. On cold opens, `analyse(candidates)` awaits all 2,000 features before calling `refine()` once.

### 2.5 Concurrency & Memory Management

- **Executors:** CPU/I/O-heavy imaging routes (`ThumbnailPipeline`, `DetailPipeline`, `DetailRenderer`, `ImageFeaturePipeline`, `RegionSharpnessAnalyzer`) wrap blocking ImageIO, Core Image, and Vision calls in `withTaskExecutorPreference(ImageWorkExecutor.userInitiated / .utility)` per `AGENTS.md` ([#146](https://github.com/mimiqdev/cloveapp/issues/146)). Exception: `PipelineGridThumbnails.swift:70` uses `Task.detached(priority: .userInitiated)` on the Swift cooperative pool for `ThumbnailRevision.read`.
- **Memory budgets & pressure gaps:** Configured steady-state cache caps total `~134 MiB` (`64 MiB` `ThumbnailCache` + `64 MiB` `DetailCache` compressed + `4 MiB` `ImageFeatureCache` + `~2 MiB` metadata/sharpness records), plus one active uncompressed `nativeRAW` (`20–200 MiB`) and transient `CIRAWFilter` / `CGDataProviderCopyData` buffers (`Q3` observed `681.1 MiB` peak RSS on Mac). Only `ThumbnailCache` attaches a `DispatchSource.makeMemoryPressureSource` handler. `DetailPipeline.releaseCachedImages()`, `ImageFeatureCache.releaseMemory()`, `ImageFeaturePipeline.pause()`, `RegionSharpnessScheduler.pause()`, and `RegionSharpnessResultStore.releaseMemory()` are never invoked anywhere in `Clove/`.

### 2.6 Device Spread (iPhone vs iPad Pro vs Duo Split)

- **Screen render targets:** `DetailMarkingView` sets `screenPixels = Int(max(screen.nativeBounds.width, screen.nativeBounds.height))` (`2868 px` on iPhone 17 Pro Max, `2752 px` on 13-inch iPad Pro M4). Both devices decode roughly the same `~3.8–5.1 MP` `screenRAW` target, so per-photo `CIRAWFilter` cost is similar in pixel count, whereas iPad Pro shows preview-to-RAW sharpness transitions across 3.8× the physical screen area at 120 Hz ProMotion.
- **Grid viewport density:** Regular-width iPad Pro (`1032–1376 pt` wide) lays out 7–9 columns × 6–8 rows (`42–72` visible tiles, up to `216` thumbnail tasks when collapsed 3-card `GroupStack`s are visible) vs 3 columns × 5–7 rows (`15–21` tiles) on iPhone—saturating `ThumbnailPipeline`'s 64-slot queue in a single screenful and cycling `ThumbnailCache`'s ~157-entry memory tier in 2–3 screenfuls.
- **Duo split:** [`BrowseShell`](../../Clove/Browsing/BrowseShell.swift) and [`DuoLayout`](../../Clove/Browsing/DuoLayout.swift) mount `GridScreen` (`30%` in `.focus`, `50%` in `.even`) and `DetailMarkingView` (`70%` / `50%`) simultaneously when unfolded. Both panes stay live: every mark or swipe in Detail triggers `BrowsingModel` observation updates across both `DetailScreen` and `GridCollectionView`, both pipelines share `ImageWorkExecutor.userInitiated` (4 concurrent slots), and `DetailMarkingView` still renders `screenRAW` at full `max(screen.nativeBounds)` rather than the 70% pane width (trading `~7%` higher decode time to avoid re-rendering when toggling split presets).

### 2.7 Startup & Folder Open

- **Entry & session setup:** [`FolderLibraryLaunch`](../../Clove/Folder/FolderLibraryLaunch.swift) restores `RecentFolderStore` entries on `@MainActor` while [`EntryScreen`](../../Clove/Browsing/EntryScreen.swift) asynchronously loads 360 px cover thumbnails from [`EntryThumbnailStore`](../../Clove/Entry/EntryThumbnailStore.swift). Opening or resuming a folder calls [`FolderLibrarySession.open`](../../Clove/Folder/FolderLibrarySession.swift), which synchronously runs `makeCaches()` (`lines 719, 1215-1234`), recreating `ThumbnailCache`, `ImageFeatureCache`, and `RegionSharpnessCache` (enumerating every file in all three `Library/Caches` subdirectories) before starting [`FolderScan`](../../Packages/CloveCore/Sources/CloveCore/FolderScan.swift).
- **Scan streaming & withholding:** [`PhotoFolderWalk`](../../Packages/CloveCore/Sources/CloveCore/PhotoFolderWalk.swift) enumerates one directory at a time, buffering all entries of each directory (`PendingDirectory`) so `RAW + JPEG + HIF + XMP` stems pair deterministically before emitting 64-photo `ScanBatch`es. Because [`PhotoOrdering`](../../Packages/CloveCore/Sources/CloveCore/Ordering/PhotoOrdering.swift) withholds `.pending` photos until capture time is known (G1 decision 3), first-grid-paint waits for the first 64-photo batch of [`MetadataReader`](../../Packages/CloveImaging/Sources/CloveImaging/Metadata/MetadataReader.swift) (`8` concurrent workers) plus `readMarks` (`FolderLibrarySession.swift:995-1008`, which calls `Data(contentsOf:)` on `<stem>.xmp` for every RAW set even when `ScannedPhotoSet.sidecar == .absent`). Each 64-photo batch sends two `@MainActor` model updates (`.photos` then `.reads`), each running `BrowsingModel.refresh()` over all accumulated photos.

> [!IMPORTANT]
> **Three Q3 Probe Blind Spots Found During Verification**
> 1. **`sony-ilce-7s-arw.arw` is a 5.1 MP (`2768×1848`, 5.9 MiB) APS-C crop RAW.** It accounts for 1,900 of the 2,000 sets (`95%`) in `browsing-2000`, masking the `2.5–4.5×` higher render cost and `4–10×` larger uncompressed pixel buffers of 20–50 MP full-frame RAWs.
> 2. **Q3 never calls `DetailPipeline.screen` (`screenRAW`) and hardcodes `detailDisplayPixels = 1320`.** Real devices run `screenPixels = 2752` (iPad Pro 13") or `2868` (iPhone 17 Pro Max) on every RAW arrival.

### 3.6 What Cannot Be Measured on This Host & Device Instrumentation Plan

Per repo rules (`docs/browsing-performance.md`), Mac measurements never substitute for physical-device claims. Four phenomena cannot be measured from a headless macOS test/CLI runner:

1. **120 Hz ProMotion CoreAnimation commit/render-server hitches (`grid-scroll-presentation` and swipe transitions):** `CloveLabKit` drives `CloveCore` and `CloveImaging` without `UICollectionView`, SwiftUI `UIHostingConfiguration` layout passes, or Metal CoreAnimation texture uploads.
2. **A19 Pro (iPhone 17 Pro Max) and M4 (iPad Pro) GPU/ANE clock scaling and thermal throttling:** Continuous `VNGenerateImageFeaturePrintRequest` + `CIRAWFilter` demosaicing over 2,000 RAWs (`15–25 s`) shares unified memory bandwidth and thermal envelope with ProMotion display compositing.
3. **iOS jetsam watermark margin:** macOS paged unified memory tolerated `681.1 MiB` RSS without pressure notifications; iOS background/foreground jetsam limits and `os_proc_available_memory()` headrooms differ by device RAM tier (8 GiB vs 16 GiB iPad Pro).
4. **External USB-C / CFexpress card reader I/O variance ([#29](https://github.com/mimiqdev/cloveapp/issues/29)):** ExFAT metadata `stat` (`ThumbnailRevision.read`) and directory enumeration latencies on external media are `10–100×` slower than APFS SSD.

**Exact instrumentation to capture on physical iPad Pro & iPhone 17 Pro Max:**
- Add lightweight `OSSignposter` intervals (`os.signpost`) around five boundaries: `GridPhotoCell.configure→pixel`, `DetailMarkingView.arrival→preview→screen`, `DetailPipeline.renderLane`, `RegionSharpnessAnalyzer.stage`, and `FolderGrouping.pass`.
- Record a 30-second trace in Xcode Instruments (`xctrace record --template 'Animation Hitches' --device <udid>`) during: (a) fast flick-scrolling a 2,000-photo burst grid on iPad Pro, and (b) rapid 3–4 photos/s detail swipes over 24–50 MP RAWs with `showsFocusRegions = true`.
- Extend Q3 `BrowsingPerformanceProbe` (`BrowsingPerformanceImages.swift`) to: (a) measure `pipeline.screen` at the device's actual `UIScreen.nativeBounds` long edge alongside `preview`, (b) remove `image.dataProvider?.data` from warm timing spans, and (c) sample `os_proc_available_memory()` on iOS alongside `memory-peak`.

## 4. Optimization Opportunities

All recommendations below preserve `AGENTS.md` invariants: **files remain the sole source of truth** (revision checks are preserved and never bypassed), **no retry or watchdog queues are introduced**, and **bounded Dispatch-backed concurrency (`ImageWorkExecutor`) is maintained**.

### O1. Gate Sharpness `.render` Acquisition Behind Interactive Fit + `+1` Prefetch, and Skip `nativeRAW` When Zero Regions Exist

- **Subsystem:** Detail swipes & Analysis pipeline ([#253](https://github.com/mimiqdev/cloveapp/issues/253), `#216`, `#239`)
- **Mechanism & code references:**
  1. **Gate interactive sharpness on fit settlement & visibility:** In [`DetailMarkingView.swift`](../../Clove/Detail/DetailMarkingView.swift) (`lines 169-174, 807-825`), do not launch `loadFocusRegions` when `!model.showsFocusRegions`. When `showsFocusRegions == true`, let metadata-only early AF (`noAutofocusMetadata` or cached `#239` disk hits) resolve immediately, or start `analyzeRegions` only after `renderFitAndPrefetch` has completed the visible photo's `screen` render (and queued `+1` preview prefetch), pausing `.nearby`/`.folder` `.pixelAcquisition` admissions in `RegionSharpnessScheduler` while an interactive `DetailPipeline` navigation generation has unfinished `screen` or `+1 prefetchScreen` work.
  2. **Cancel obsolete `.analysis` queued jobs on swipe & prioritize `.prefetch` `+1` screen over `.analysis`:** In [`DetailPipeline.swift`](../../Packages/CloveImaging/Sources/CloveImaging/Detail/DetailPipeline.swift) (`lines 124, 344-354`), `.prefetch` currently has `DetailPriority = 1` while `.analysis` has `0` (so queued `+1 prefetchScreen` already beats queued `.analysis`), **except** `beginNavigation` (`line 124`) skips `job.priority == .analysis`, allowing stale `.analysis` jobs from the just-left photo to claim the `.render` worker in the window between `beginNavigation` and `navigate(to:)`. Cancel non-matching `.analysis` jobs in `beginNavigation` as well.
  3. **Skip `.pixelAcquisition` when a photo has zero AF boxes and zero faces:** In [`RegionSharpnessAnalyzer.swift`](../../Packages/CloveImaging/Sources/CloveImaging/Sharpness/RegionSharpnessAnalyzer.swift) (`lines 150-200`), when `autofocus` returns `.failure` (no AF metadata), `await detection` *before* entering `.pixelAcquisition`. If `detectedFaces` is also empty, return `RegionSharpnessAnalysis` immediately with zero high-resolution decode! Even when `autofocus` succeeds, consider reusing `DetailCache`'s `native` or matching `cameraPreviewFirst` companion (`DetailRegionSharpnessReading.swift:54-59` currently hardcodes `mode: .rawFirst`).
- **Expected gain:**
  - **Measured (`Table 3.4`, 20 MP CR3 @ 2752 px):** Gating sharpness behind `screenRAW` cuts 800 ms-cadence `screen` `p95` from `795.2 ms` to `409.6 ms` (`-48%`), cuts mean `screen` latency from `228.8 ms` to `96.3 ms` (`-58%`), and boosts `+1` `screenRAW` prefetch hits from `33%` (`4/12`) to `75%` (`9/12`, or `92%` when `showsFocusRegions == false`).
  - Skipping `.pixelAcquisition` on 0-AF / 0-face photos eliminates **100% of `nativeRAW` decodes** (`157–484+ ms` each) on landscapes, street, product, and manual-focus shots across the entire 2,000-photo `.folder` background pass.
- **Cost & risk:** Medium (`2–3 days`). Low risk: `RegionSharpnessAnalysis` semantics and `#239` disk records remain identical (0-region records already contain empty region arrays). Trade-off: when `autofocus` fails *and* faces exist, waiting for `detection` (`~25–40 ms` on 800 px preview) before starting `nativeRAW` serializes those `~30 ms` instead of overlapping them—a tiny cost compared to saving `380–1,000 ms` on every face-free photo.
- **Interactions:** Multiplies the effectiveness of **O2** (`+1` prefetch actually gets the `.render` lane) and reduces peak RSS (**O6/O7**).

### O2. Immediate Parallel Preview Prefetch, Non-Blocking Cold `preview`, and Zero-Blank-Flash Arrival

- **Subsystem:** Detail navigation swipes (`#253`)
- **Mechanism & code references:**
  1. **Start `±2` preview prefetch immediately on the `.preview` lane:** [`DetailPipeline`](../../Packages/CloveImaging/Sources/CloveImaging/Detail/DetailPipeline.swift) already isolates `.preview` (`previewWorkers = 2`) from `.render` (`1` worker), yet [`DetailMarkingView.renderFitAndPrefetch`](../../Clove/Detail/DetailMarkingView.swift) (`lines 925-939`) waits for `images.screen` (`110–310 ms`) to finish before calling `images.prefetch(previewRequests)`. Dispatch `±2` `prefetchPreview` immediately after `current` `preview` lands (or concurrently at `.prefetch` priority on arrival) while `screen` runs on `.render`.
  2. **Remove `CIRAWFilter.extent` and synchronous JPEG-0.9 encoding from the critical path of `DetailPipeline.preview`:** In [`DetailPipeline.swift`](../../Packages/CloveImaging/Sources/CloveImaging/Detail/DetailPipeline.swift) (`lines 505, 522, 577-588`), `prepare` calls `DetailNativeSizeReader` (`CIRAWFilter(imageURL:)?.outputImage?.extent` = `40–87 ms`) only to populate `fullResolutionSize` (used for the zoom cap in `DetailZoomView`, not needed to display fit preview!), and `perform` synchronously JPEG-0.9 encodes `DetailCompressedImage` (`9–18 ms`) before returning `DetailResult`. Instead: read `kCGImagePropertyPixelWidth/Height` (or EXIF/SubIFD dimensions via `CGImageSourceCopyPropertiesAtIndex` in `<1 ms`, falling back to `CIRAWFilter` lazily on `screen`/zoom) and return the decoded `DetailImage` immediately while storing `DetailCompressedImage` into `DetailCache` asynchronously on the worker.
  3. **Synchronous warm arrival (no unconditional `shown = nil`):** In [`DetailMarkingView.loadPreview`](../../Clove/Detail/DetailMarkingView.swift) (`lines 758-765`), keep the outgoing image only until checking a synchronous memory fast path (`ThumbnailCache` memory hit for the 400 px placeholder, or `DetailCache` if pre-decoded `+1` bitmap is held), avoiding the guaranteed `nil` frame between swipes. Holding a single pre-decoded `CGImage` slot in `DetailCache` for the `+1` prefetched neighbor (`~16–24 MiB` at `2752 px`) also eliminates the `12.5–16.2 ms` JPEG-0.9 decode tax on forward swipes.
- **Expected gain:**
  - **Measured (`Table 3.3` & `Table 3.4`):** Removing `CIRAWFilter.extent` + JPEG-0.9 encode from `preview`'s return path cuts cold first-preview latency on 20–26 MP RAWs from `105–166 ms` to **`~35–67 ms` (`2.1–2.8×` faster)**. Immediate `.preview`-lane neighbor prefetch cuts brisk-culling (`400 ms` dwell) arrival-to-preview `p50` on 20 MP CR3 from `140.9 ms` to **`~15–18 ms` (`8×` faster)** (already demonstrated empirically in Table 3.4 Scenario 2 when sharpness accidentally warmed `.preview`!).
- **Cost & risk:** Medium (`2–4 days`). Low–Medium risk: verify EXIF orientation swap (`5–8`) when reading dimensions from ImageIO properties so `DetailZoomView`'s initial aspect/zoom bounds match `CIRAWFilter` output; `screenRAW` still confirms exact `CIRAWFilter` dimensions `~200 ms` later.

### O3. Synchronous `ThumbnailCache` Memory Lookup in `GridPhotoCell`, In-Flight Coalescing, and `utimes`-Free Disk Reads

- **Subsystem:** Grid scrolling & `ThumbnailPipeline`
- **Mechanism & code references:**
  1. **Synchronous memory-tier cell configuration:** Add `public func memoryResult(forKey / request) -> ThumbnailResult?` on [`ThumbnailCache`](../../Packages/CloveImaging/Sources/CloveImaging/Thumbnails/ThumbnailCache.swift) (`lines 114-118`, lock-only dictionary lookup, zero disk I/O) and expose a synchronous lookup on `GridThumbnailLoading` keyed by `(url, ScannedImageFile.revision)` (already recorded during scan!). In [`GridPhotoCell.configure`](../../Clove/Grid/GridPhotoCell.swift) (`lines 50-58`), check memory synchronously for the representative tile and up to two peeking `GroupStack` members *before* building `UIHostingConfiguration`—building the hosting configuration **once** with final images on every warm scroll/diffable-datasource reconfigure instead of `nil` → async Task → 2–3 hosting rebuilds.
  2. **Coalesce in-flight `ThumbnailPipeline` requests & stop `willDisplay` prefetch self-sabotage:** Key in-flight jobs in [`ThumbnailPipeline`](../../Packages/CloveImaging/Sources/CloveImaging/Thumbnails/ThumbnailPipeline.swift) by `(source, revision, targetPixels, locationIdentity)` so multiple callers (e.g. `prefetchItemsAt` followed milliseconds later by `willDisplay`, or `GridScreen` + `DetailFilmstrip` in Duo) join the existing decode and promote `.prefetch` → `.visible` instead of cancelling and restarting from scratch (`GridCollectionView.swift:538`).
  3. **Pass scan's `ThumbnailRevision` & eliminate redundant `stat` + per-hit `utimes` writes:** Route `PipelineGridThumbnails` revision verification onto `ImageWorkExecutor` instead of `Task.detached(priority: .userInitiated)` (`PipelineGridThumbnails.swift:70`), pass the revision from `ScannedImageFile` for initial loads (keeping a single post-decode revision check in `ThumbnailPipeline` on cache misses so `AGENTS.md` files-are-truth still catches mid-decode rewrites, dropping `3×` `stat` to `1×` on misses and `0×` on hits), and remove `FileManager.default.setAttributes([.modificationDate: now])` from [`ThumbnailCache.result(for:)`](../../Packages/CloveImaging/Sources/CloveImaging/Thumbnails/ThumbnailCache.swift) (`lines 160-161`, and similarly in `ImageFeatureCache.swift:383` and `RegionSharpnessCache.swift:290`). `state.disk[key]?.access` already tracks exact LRU in memory during the session; if cross-launch LRU persistence matters, flush touched timestamps lazily in small batches or only when `now.timeIntervalSince(entry.access) > 3600`.
- **Expected gain:**
  - **Measured (`Table 3.5`):** Synchronous memory hit takes `75 µs` (or `<5 µs` if keyed by `PhotoIdentity` / precomputed digest in the view layer), eliminating `100%` of warm cell blank flashes and cutting `UIHostingConfiguration` updates per cell from `2–4×` to `1×`. Removing `utimes` + `dataProvider?.data` (`O7`) drops serial disk-cache read latency from `0.63 ms` to `0.45 ms` (`-28.6%`) and eliminates thousands of unnecessary APFS metadata writes per scroll pass.
- **Cost & risk:** Medium (`3–4 days`). Low–Medium risk: when a folder's file changes externally, `FolderLibrarySession` rescans and updates `ScannedImageFile` revisions; preserving `ThumbnailPipeline`'s miss-path revision check ensures modified files never poison the cache.

### O4. Short-Circuit `FolderGrouping` Feature Pass on `SimilarGroupsCache` Hits & Refine Incrementally on Cold Opens

- **Subsystem:** Similarity grouping (`FolderGrouping`, `SimilarGrouping`)
- **Mechanism & code references:**
  1. **Guard `analyse(candidates)` on `needsAnalysis`:** In [`FolderGrouping.swift`](../../Clove/Grouping/FolderGrouping.swift) (`lines 238-254`), `startAnalysis(needsAnalysis:)` notifies `analysisChanged(needsAnalysis)` and then unconditionally executes `await analyse(candidates)`. Add `guard needsAnalysis else { return }` immediately after `analysisChanged(false)`. (`SimilarGrouping.setSensitivity` already invalidates `cacheIsAuthoritative` and triggers a fresh pass if the user later drags the sensitivity slider!)
  2. **Incremental per-run `refine()` during cold grouping:** During a cold 2,000-photo open (`20.4 s` on M2 Pro), `FolderGrouping.analyse` (`lines 303-318`) collects all 2,000 features before calling `grouping.refine()` once. Because `SimilarGrouping` only compares adjacent photos *within* each candidate time-run (`Δt ≤ 3.0 s`), features can be requested in visible/ordered burst order and `refine()` (which takes only **`7.93 ms` in Release** for the entire 2,000-photo folder!) can run every ~1–2 seconds or per completed burst batch so visible stacks settle within the first second instead of waiting 20 seconds.
- **Expected gain:**
  - **Measured (`Table 3.2`):** Skipping the redundant feature pass cuts warm grouping total time on `browsing-2000` from **`426.1 ms` to `10.05 ms` in Release (`42.4×` faster)** and from **`749.3 ms` to `261.9 ms` in Debug**, eliminates `1,975` plist reads + `1,975` `utimes` writes + `2,000` `stat`s on every warm open, and prevents multi-second Vision recomputation when `ImageFeatureCache` (`8 MiB`, ~2,400 photos) evicts entries across multiple folders while `SimilarGroupsCache` still holds the finished groups.
- **Cost & risk:** Small (`0.5–1 day` for warm short-circuit; `+1.5 days` for incremental cold refinement). Very low risk: verify with existing `FolderGroupingTests` that changing sensitivity after a warm cache hit still triggers `analyse(candidates)` (`SimilarGrouping` sets `cacheIsAuthoritative = false` on sensitivity change, so `FolderGrouping.setSensitivity` simply needs to start `analyse` when `!cacheIsAuthoritative` and features aren't loaded yet).

### O5. Eliminate `@MainActor` Frame-Budget Spikes (`DetailFilmstrip`, `BrowsingModel.photos`, `DetailSource.read`, Scan Double-Refresh)

- **Subsystem:** Concurrency, Detail UI, Grid UI, Startup, Duo Split
- **Mechanism & code references:**
  1. **Index `DetailFilmstrip.entries` in `O(N + G)` and compute once per body:** [`DetailFilmstrip.swift`](../../Clove/Detail/DetailFilmstrip.swift) (`lines 31, 41, 51-71`) accesses the computed `entries` property twice (`body` and `scrollToCurrent`), and inside `entries` runs `photos.filter { members.contains($0.id) }` for every group (`O(N × G)` with `Array.contains`). Precompute `let photoOrderIndex = Dictionary(uniqueKeysWithValues: photos.enumerated().map { ($1.id, $0) })` so each group filters/sorts in `O(|group|)` instead of `O(N)`, and memoize `entries` when `(photos, groups, isGroupingEnabled, collapsedCurrentGroup)` have not changed.
  2. **Memoize `BrowsingModel.photos` inside `refresh()`:** [`BrowsingModel.swift`](../../Clove/Browsing/BrowsingModel.swift) (`lines 210-215`) rebuilds `PhotoOrdering(photos: storedPhotos)` and sorts 2,000 structs on *every property read* (`GridScreen.body` reads `model.photos` 3+ times; `DetailScreen` + `DetailFilmstrip` read it 3+ times; in Duo split **both** run on every mark/swipe!). Maintain a single `private var ordering = PhotoOrdering()` incrementally (using `PhotoOrdering.insert`, `setTime`, `setMarks`, `remove`, which already exist in [`PhotoOrdering.swift`](../../Packages/CloveCore/Sources/CloveCore/Ordering/PhotoOrdering.swift)!) and store the sorted/filtered `[GridPhoto]` array whenever `storedPhotos`, `order`, or `filter` mutates.
  3. **Move `DetailSource.read` off `@MainActor`:** [`PipelineDetailImages.swift`](../../Clove/Detail/PipelineDetailImages.swift) (`lines 93, 125-131, 212-226, 250`) runs `DetailSource.read` (`removeAllCachedResourceValues` + `stat`) synchronously on `@MainActor` for `current`, `prefetch`, and `analyzeRegions` (`13–60+` files per swipe). Build `DetailRequest` / `RegionSharpnessRequest` inside the async task on `ImageWorkExecutor` instead.
  4. **Guard `.absent` XMP reads & coalesce per-batch scan updates:** In [`FolderLibrarySession.swift`](../../Clove/Folder/FolderLibrarySession.swift) (`lines 995-1008`), only read `<stem>.xmp` when `ScannedPhotoSet.sidecar.resolvedURL != nil` instead of hitting `ENOENT` on every unmarked RAW set. Combine `.photos` (which are all `.pending` and withheld from the grid anyway) with `.reads` per 64-photo batch to halve `BrowsingModel.refresh()` invocations during folder open (`64 → 32`).
- **Expected gain:**
  - **Measured (`Table 3.5`):** Cuts `DetailFilmstrip.entries` per swipe from **`11.73 ms` to `0.51 ms` (`23×` faster for the swipe**, reclaiming an entire 120 Hz frame on `@MainActor`), saves **`4.9–8.2 ms`** of redundant `PhotoOrdering` sorting per SwiftUI pass (especially impactful in Duo split where Grid + Detail update together), saves `13.2 ms` of `ENOENT` syscalls on local SSD (`100+ ms` on external cards), and eliminates main-thread filesystem stalls on external media.
- **Cost & risk:** Small–Medium (`1.5–2.5 days`). Low risk: `PhotoOrdering` already implements tested mutating methods (`insert`, `setTime`, `setMarks`, `remove`).

### O6. Share Disk/Memory Cache Instances Across Folder Opens & Wire App-Wide Memory-Pressure Handling

- **Subsystem:** Startup / folder open & Concurrency / memory
- **Mechanism & code references:**
  1. **Hoist `Caches` (`ThumbnailCache`, `ImageFeatureCache`, `RegionSharpnessCache`) to `FolderLibrary` lifetime:** [`FolderLibrarySession.makeCaches()`](../../Clove/Folder/FolderLibrarySession.swift) (`lines 719, 1215-1234`) instantiates brand-new cache objects on every `openFolder`. Because every cache key already encodes `locationIdentity` (or full standardized path + revision), sharing one `Caches` bundle across folder sessions is safe by construction, keeps `64 MiB` of decoded thumbnails + `4 MiB` of features warm when switching back to a recent folder from `EntryScreen`, and runs `contentsOfDirectory` cache indexing once at app launch (off `@MainActor`) instead of on every folder open.
  2. **Wire iOS memory-pressure notifications to all five caches/pipelines:** Attach a session-level `DispatchSource.makeMemoryPressureSource(eventMask: [.warning, .critical])` (and `UIApplication.didReceiveMemoryWarningNotification`) in `FolderLibrarySession` that invokes:
     - On `.warning`: `detailPipeline.releaseCachedImages()` (or trims compressed `DetailCache` and releases non-visible native buffers), `featureCache.releaseMemory()`, `sharpnessResults.releaseMemory()`.
     - On `.critical`: additionally calls `await featurePipeline.pause()` and `await sharpnessScheduler.pause()`, resuming once pressure clears or on next explicit user action.
- **Expected gain:**
  - **Measured (`Table 3.2` & `Table 3.5`):** Saves `22–250+ ms` of synchronous cache-directory enumeration on every folder open, turns Entry → recent-folder reopen into an instant `75 µs`/cell memory hit for the first screenful, and allows `DetailCache` (`64 MiB` + native RAW) to shed `100–250+ MiB` immediately under iOS memory pressure instead of risking jetsam near `681+ MiB` RSS.
- **Cost & risk:** Small (`1–1.5 days`). Low risk: all purge and pause APIs (`releaseCachedImages`, `releaseMemory`, `pause`) are already implemented and unit-tested in `CloveImaging`—they are simply unwired in `Clove/`.

### O7. Remove Redundant `image.dataProvider?.data` Full-Buffer Copies After Eager Decodes

- **Subsystem:** Detail, Thumbnails, Memory (`DetailCompressedImage`, `DetailRenderer`, `ThumbnailCache`, `ThumbnailExtractor`, `BrowsingPerformanceImages`)
- **Mechanism & code references:**
  - `DetailCompressedImage.decoded()` ([`DetailCompressedImage.swift:41-43`](../../Packages/CloveImaging/Sources/CloveImaging/Detail/DetailCompressedImage.swift)), `ThumbnailCache.result(for:)` ([`ThumbnailCache.swift:129-130`](../../Packages/CloveImaging/Sources/CloveImaging/Thumbnails/ThumbnailCache.swift)), and `DetailRenderer` ([`DetailRenderer.swift:78, 121, 197`](../../Packages/CloveImaging/Sources/CloveImaging/Detail/DetailRenderer.swift)) already force eager bitmap materialization (`kCGImageSourceShouldCacheImmediately: true` or `CIContext.createCGImage(..., format: .RGBA8)`), and **then** call `image.dataProvider?.data` (`CGDataProviderCopyData`), which allocates a second full uncompressed RGBA buffer and `memcpy`s every pixel just to check `!= nil` / `CFDataGetLength > 0`.
  - For `CIContext.createCGImage` (`DetailRenderer.raw`, `line 117`), `createCGImage` already renders eagerly into an owned bitmap (`nil` is returned on render failure — verified against S2's comment at `line 123`); checking `image.width > 0 && image.height > 0 && image.bytesPerRow > 0` (or reading 1 pixel via a `1×1` `CGContext` if paranoia is required for exotic RAW decoders) avoids allocating a **second `80–200 MiB` copy** of every 20–50 MP `nativeRAW`! Similarly, in `DetailCompressedImage.decoded()` and `ThumbnailCache.result(for:)`, we encoded those valid baseline JPEGs ourselves; `kCGImageSourceShouldCacheImmediately: true` + `width > 0 && height > 0` suffices.
- **Expected gain:**
  - **Measured (`Table 3.3` & `Table 3.5`):** Cuts `DetailCompressedImage` decode time by `24–30%` (`7.01 → 5.33 ms` on CR3 preview; `~3–5 ms` saved on every `2752 px` `screenRAW` cache hit), cuts transient peak memory during a 50 MP `nativeRAW` render by **`~200 MiB`**, and fixes Q3's warm `raw-focus` measurement distortion (`49.8–130.2 ms` → `0.09 ms`).
- **Cost & risk:** Small (`1 day`). Low risk: keep `ThumbnailExtractor` / `DetailRenderer.materialized` tested against `CloveImagingTests`'s corrupt/truncated fixture cases to confirm `CGImageSourceCreateThumbnailAtIndex` with `kCGImageSourceShouldCacheImmediately: true` still returns `nil` on truncated streams without needing `CGDataProviderCopyData`.

### O8. Device-Aware Cache Sizing & Duo `screenPixels` Policy

- **Subsystem:** Device spread (iPad Pro, iPhone 17 Pro Max, Duo)
- **Mechanism & code references:**
  - **Scale memory tiers by physical memory (`ProcessInfo.processInfo.physicalMemory` / `os_proc_available_memory()`):** On ≥8 GiB devices (iPhone 17 Pro Max 8–12 GiB, iPad Pro M4 8–16 GiB), once **O6** wires memory-pressure purging, raising `ThumbnailCache.memoryBytes` from `64 MiB` (~157 tiles = ~2.5 iPad Pro screens) to `128 MiB` (~314 tiles = ~5–6 iPad Pro screens) and `DetailCache.compressedBytes` from `64 MiB` (~17 ProRAWs / ~29 CR3s) to `96–128 MiB` (~26–34 ProRAWs / ~45–60 CR3s) prevents back-scroll and burst-review cache thrashing on iPad Pro.
  - **Keep `DetailMarkingView`'s full-screen `screenPixels` in Duo split (documented trade-off):** Table 3.3 (`SUPP 1`) measured `screenRAW` at `1926 px` (Duo 70% focus split) vs `2752 px` (full screen): `264.4 ms` vs `282.9 ms` on CR3 (`-6.5%`), `234.1 ms` vs `248.9 ms` on RAF (`-5.9%`). Because saving `15–18 ms` is minor compared to avoiding a full `280 ms` re-render when toggling Duo split presets (`focus` ↔ `even` ↔ single-pane), keeping fixed `max(screen.nativeBounds)` for `screenPixels` is the right design.
- **Expected gain:** Doubles warm thumbnail retention on iPad Pro (`~157 → ~314` tiles) and extends `DetailCache` full-burst retention by `1.5–2×` on ProRAW/high-detail RAW sets.
- **Cost & risk:** Small (`0.5–1 day`), gated on **O6** landing first so any enlarged cache purges deterministically on `.warning`.

## 5. Non-Opportunities (Examined and Deliberately Not Recommended)

### N1. Persisting `screenRAW` or `nativeRAW` Renders to Disk
- **Why examined:** Cold `screenRAW` at `2752 px` takes `166–305 ms` across 12–26 MP RAWs; a disk cache could serve cross-session revisits in `~14 ms`.
- **Why rejected:** Explicitly ruled out in [#239](https://github.com/mimiqdev/cloveapp/issues/239) and counter-productive at folder scale. Storing `1.3–2.3 MiB` `screenRAW` JPEGs across 2,000 photos writes `2.6–4.6 GiB` per folder, churns SSD wear, requires eviction sweeps during active culling, and offers zero help on the first culling pass where photographers spend >90% of their time. **O1 + O2** already hide `screenRAW` behind a `50 ms` preview and `75–92%` `+1` in-memory prefetch hits.

### N2. Replacing Per-File Disk Caches with SQLite or Core Data
- **Why examined:** `ThumbnailCache`, `ImageFeatureCache`, and `RegionSharpnessCache` store one file per key and enumerate their directories in `init`.
- **Why rejected:** Violates `AGENTS.md` simplicity and `#239`'s explicit architecture without solving an actual bottleneck. Once **O4** stops re-reading 1,975 `.feature` files on warm opens, **O6** constructs the caches once per app launch instead of per folder open, and **O3** drops per-read `utimes` writes, per-file APFS lookups take `0.45 ms` (`ThumbnailCache`) with atomic file-replacement crash safety and zero database lock/WAL corruption surface.

### N3. Increasing `DetailPipeline` Concurrent `.render` Workers Above `1`
- **Why examined:** Allowing 2 concurrent `.render` workers would let `nativeRAW` (for sharpness) and `screenRAW` (for fit display) run simultaneously.
- **Why rejected:** Each 20–50 MP `CIRAWFilter` render allocates `80–200+ MiB` of transient Core Image + output RGBA buffers and saturates Metal/P-core demosaic throughput. Running two concurrent RAW renders would spike process RSS well above `900–1,100 MiB` (triggering iOS jetsam) and slow *both* renders via memory-bandwidth contention, making interactive `screenRAW` *slower* than gating sharpness behind `screenRAW` (**O1**).

### N4. Dropping Filesystem Revision Checks (`ThumbnailRevision`) During Browsing
- **Why examined:** Skipping `size + mtime` checks altogether would remove every `stat` call from thumbnail and detail paths.
- **Why rejected:** Violates `AGENTS.md`'s core rule that **files are the source of truth**—if an external editor or card rewrite replaces a file at the same path, Clove must never display stale cached pixels or stale sharpness scores. Moving `DetailSource.read` off `@MainActor` (**O5**) and reusing the fresh `ScannedImageFile` revision scanned by `PhotoFolderWalk` while keeping `ThumbnailPipeline`'s miss-path check (**O3**) captures >90% of the latency win without weakening staleness guarantees.

### N5. Rewriting `GridTile` from `UIHostingConfiguration` to Manual `UIView` / `CALayer` Subviews Immediately
- **Why examined:** SwiftUI `UIHostingConfiguration` with nested `GeometryReader`s (`GridPhotoCell.swift:227`, `GroupStack.swift:12`) carries higher per-reconfigure CPU cost than raw `CALayer.contents`.
- **Why rejected *for now*:** Today's grid cell churn is dominated by `GridPhotoCell.configure` rebuilding `UIHostingConfiguration` `2–4×` per cell due to unconditional `thumbnail = nil` async hops and `willDisplay` prefetch cancellation (**O3**). Rewriting badges, marks, burst counts, and peeking stacks in manual UIKit duplicates layout logic across iPhone, iPad, and Duo split. Re-evaluate only if physical-device `xctrace` `Animation Hitches` still attributes >2 ms/frame to `UIHostingConfiguration` *after* **O3** (plus replacing the inner `GeometryReader` with simple proportional layout math) lands.

### N6. Adding Retry Queues or Speculative Multi-Resolution RAW Pyramids
- **Why examined:** Transient `queueFull` errors during extreme flick-scrolling or zoom transitions could be retried automatically, or `DetailPipeline` could render an intermediate `1000 px` draft RAW before `2752 px`.
- **Why rejected:** `AGENTS.md` explicitly forbids retry machinery (`queueFull` is expected backpressure when cells scroll past faster than decode; `willDisplay` naturally re-requests visible cells), and `DetailRenderer` explicitly disables `CIRAWFilter` draft mode (`DetailRenderer.swift:114`) because embedded camera previews (`1616–2000 px`) already arrive in `35–67 ms` (with **O2**) at higher visual fidelity than half-baked draft demosaics.

## 6. Recommended Implementation Sequence

Each phase is self-contained, testable in isolation, and ordered by `(user-visible gain ÷ implementation risk)`.

### Phase 0 — Measurement Visibility (`~1 day`, Prerequisite for Honest Validation)
1. **Fix Q3 `BrowsingPerformanceProbe` blind spots:** Add `DetailPipeline.screen` (`screenRAW`) at native screen long edge (`2752` / `2868 px`), include a 20+ MP RAW fixture alongside `sony-ilce-7s-arw` in detail benchmarks, and remove `image.dataProvider?.data` from warm timing spans.
2. **Add `OSSignposter` intervals** around grid cell configure, detail arrival → preview → screen, `.render` lane occupancy, and sharpness stages so physical iPad Pro / iPhone 17 Pro Max `xctrace` runs before and after Phases 1–3 are directly comparable.

### Phase 1 — Low-Risk High-Leverage Quick Wins (`~3–4 days`)
1. **O4 (warm part):** Guard `FolderGrouping.startAnalysis` on `needsAnalysis` (`426 ms → 10 ms` warm grouping; zero wasted `.feature` disk churn).
2. **O5:** Index `DetailFilmstrip.entries` in `O(N + G)` (`11.7 ms → 0.5 ms` on `@MainActor`), cache ordered `BrowsingModel.photos` via incremental `PhotoOrdering`, move `DetailSource.read` off `@MainActor` in `PipelineDetailImages`, and skip `.absent` XMP `Data(contentsOf:)` calls in `readMarks`.
3. **O6 + O7:** Hoist `Caches` (`ThumbnailCache`, `ImageFeatureCache`, `RegionSharpnessCache`) to `FolderLibrary` lifetime, wire `DispatchSource` / `didReceiveMemoryWarningNotification` across all caches/schedulers, and drop redundant `image.dataProvider?.data` full-buffer copies on owned/cached images.

### Phase 2 — Detail Swipe Smoothness (`#253` Resolution, `~4–5 days`)
1. **O1:** Skip `loadFocusRegions` when `!showsFocusRegions`; gate interactive/background sharpness `.pixelAcquisition` behind `screenRAW` + `+1` prefetch settlement; cancel non-current `.analysis` jobs in `beginNavigation`; and `await detection` before `.pixelAcquisition` when `autofocus` has no metadata so 0-AF / 0-face photos never decode `nativeRAW`.
2. **O2:** Start `±2` `prefetchPreview` immediately on arrival on the `.preview` lane; decouple `DetailNativeSizeReader` (`CIRAWFilter.extent`) and JPEG-0.9 cache encoding from blocking `DetailPipeline.preview`; and serve warm memory hits synchronously on arrival so `shown` never flashes `nil` between swipes.
3. **Device check:** Unpause and validate [#253](https://github.com/mimiqdev/cloveapp/issues/253) on physical iPad Pro with `xctrace` `Animation Hitches` over 24–50 MP RAW bursts.

### Phase 3 — 120 Hz Grid Polish, Incremental Cold Grouping & Cache Tuning (`~4–5 days`)
1. **O3:** Add synchronous `ThumbnailCache.memoryResult` in `GridPhotoCell.configure` (single `UIHostingConfiguration` build on warm cells), coalesce in-flight `ThumbnailPipeline` jobs (promoting `.prefetch` → `.visible` instead of cancelling in `willDisplay`), route `PipelineGridThumbnails` onto `ImageWorkExecutor` with `ScannedImageFile` revisions, and remove per-read `utimes` writes on cache hits.
2. **O4 (cold part) + O8:** Add incremental per-burst `refine()` during cold `FolderGrouping` passes so burst stacks settle progressively within 1–2 seconds of folder open, and tune `ThumbnailCache` / `DetailCache` memory caps for ≥8 GiB devices on physical iPhone 17 Pro Max and iPad Pro.
